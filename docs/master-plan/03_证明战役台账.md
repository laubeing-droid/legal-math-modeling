### CI 证据落盘（P2-26）

审计的指控是：仓内 markdown 具名引用了一批 Actions run 号当证据（现账为 22 个，数以 `--check` 末行输出为准），但仓内没有
任何一个 run 的可核信息——第三方要复核就得自己有 `gh` 权限。现由
`scripts/ci/build_ci_run_index.py` 把每个被引用 run 的 subject commit、分支、触发
事件、结论、逐作业结论与工件数连同**引用位置 file:line** 一起落到
`docs/formal-release/ci_run_index.{json,md}`；该文件是 Actions 元数据快照，不是发布
证书，其 `authority_note` 自己写明这点。`--check` 不联网，只核"被引用的号是否都在账上、
记录是否完整"，因此新增引用而不重生成即红。

顺带把审计对象那一拍的两条最新运行也具名入账：run `36259479766`（head `b57d4aa`，
main，push，**success**，即本次审计 subject 的绿 run）与 run `36258179200`
（head `1488685`，main，push，**failure**——同一条 P-083 链在上一拍是红的，
"绿"从来不是继承来的）。快照同时给出一个此前无法在仓内核对的分布：非 success 的条数与清单由生成表末行给出（`docs/formal-release/ci_run_index.md`，逐号列 conclusion 与作业通过比），台账不复制这个数。逐处引用回看，这些号
在原文里都是作为**失败轨迹**叙述的（`baseline.md:11` 写 "FAIL"、
`ROOT_CONSTRUCTION_RECORD.md:126` 写 "失败 run"），故不另立缺陷；把它们列出来的用处，
是让"哪些号是绿的"这件事第一次可以在仓内一次看全。

### 胜率管线的第三步对象（军令件二补全）

`Mandate/CohortInterval.lean` 给出第三步要消费的对象：把母体率写成 **add-one 区间**，
两端都是内核的 `Rate`（交叉相乘序 `≤ₛ`），全文件无除法、无浮点。
证得的性质：区间有序（`low_le_high`）、两端不越出 [0,1]、两端严格分离
（`low_num_lt_high_num`，区间不是伪装的点）、加一个胜诉两端同向上移
（`low_le_added_success`/`high_le_added_success`，是"整体平移"不是"劈开"）、
母体变大而下端点不升（`low_antitone_in_size`）、无母体则无区间
（`intervalOf_none_without_cohort`）、零胜诉仍有合法区间（退化为纯先验而非崩成未定义）。
`Cohort` 把 `successes ≤ size` 设成字段：缺了它"胜数/规模"只是两个不相关的数，
单位区间那两条就是**假的**——这条约束是写证时被自家门逼出来的，不是装饰。
内核消费者增至 4 个（CohortRate/CohortInterval/StructureInvariants/GameTree）。
