## 四、python-gates 剩余红的成因（含一处我自己判错并已撤回的诊断）

**先把红轮点名**：run 37025459941（subject `8515dc2`）这一轮 push **判 failure**，
红的是 `python-gates` 与它的两个下游（`seven-axis-acceptance`、`final-gate`），
同一轮的 `lean-full-clean-build` 判 success。构建面与门禁面互不蕴含，这一轮就是例子。

**先撤回一条错的**：本节先前把清单哈希不一致归因于"生成脚本写 LF、Git 转 CRLF"。
实测**不成立**：仓库早有 `.gitattributes` 钉 `*.lean text eol=lf` 且 `core.autocrlf=false`，
`git show HEAD:<path>` 与工作树字节**逐字节相同**。那条诊断是猜的，写进文档时也没验，
属于"把没查全的机制说成原因"——记在这里是为了让后来的读手不要照着它去改属性。

真正的原因是**账与账的作用域口径不同**，实测分三段：

1. **清单过期**：`theorem_manifest.json` 记录的是重算之前的文件哈希，根扩大后没跟着重算，
   于是 `hash mismatch: JurisLean.lean` 一类。重算即消，本轮已做。
2. **闭包账与形状账一度差 80 条**（3450 对 3530）。两者都以同一棵 `JurisLean/` 为准，
   差在**生成时刻**不同：一次在 AxiomAudit 那批新增具名之前，一次在之后。
   同一时刻连排三份生成器后两侧都读得 3530，且写盘的派生段现在**落笔前先核实
   三类闭合之和等于总数、形状账与闭包账总数一致**，不成立就拒绝写。
3. **仍未闭的（第三次修正，这次是查到底了）**：`test_census_and_manifest_count_the_same_declarations`
   比的**不是**我一直在重算的 `theorem_manifest.json`，而是 `theorem_inventory_v3.json`。
   实测：`theorem_manifest.json` 的包作用域 `theorem_count` 求和 = **3530**，与闭包账**完全一致**；
   而 `theorem_inventory_v3.json` 停在 **297 个文件 / 3240 条**，因为**它在仓库里没有任何生成器**——
   `grep -rn "theorem_inventory_v3" scripts/ tools/` 只命中把 v3 当**输入**读的脚本（普查、形状账、清单、锚点门、再生序列），
   没有一个写它。⇒ 这条门是**拿一个活的计数去比一件没人再生成的孤儿工件**：它只会随根增长单调变红，
   永远不可能被"重算"抹平。我先前两次诊断都错了——先赖 LF/CRLF（已撤回），
   再赖"清单生成器的包作用域没走共享语法规则"（也是错的，清单侧本来就走对了，3530 对 3530）。
   **修法只有两条，都要 Owner 点头**：① 给 v3 补一个生成器并纳入再生序列；
   ② 把该断言改为对照 `theorem_manifest.json`（这是修**指针**，不是放宽判据——它仍然要求两份独立工件的总数相等）。
   同族另两条（证书逐条对照、普查自报盲区）同样落在 v3 这个孤儿工件上，先一并挂着。

论文侧另有一处已处理：两语种各有一段**派生记账段**，由
`_seams_build_logs/rewrite_derived_accounting.py` 从工件整体重写（截旧补新，不是在过期数字上再叠一层更正）。
