# WBS-8 规格：案卷 → 裁决链通道（2026-10-05，第二轮复核 F3 委托）

> 本规格只出证明义务与输入字段，**不动 Lean 源**。实施另起轮次，实施前缺口 1
> 维持"部分闭合：仅达 `HornSystem` 骨架，未接裁决链"。

## 〇、为什么需要本通道

第二轮独立复核 B3 坐实：`Seams/CaseInput.lean` 交付的是"案卷 JSON → `HornSystem`"
的逐字段照搬；链谓词六支（`StatuteChainOn`，`StatuteChain.lean:618`）消费的是手写
`UnifiedModel`（`instanceM`），两者之间全仓没有一条消费边。要让"一份案卷"走到
"链的六支"，必须新造三段构造，每段都有各自独立的证明义务，且每段里都藏着
**实质是法律判断、无法机械化**的步骤——本规格把这些步骤点名，防止下一轮再把
"管道接通"误记成"案件跑通"。

## 一、段一：`CaseFile` → `DungAAF` 论点集与攻击边

**目标**：从案卷数据构造一台 Dung 抽象论辩框架（论点集＋攻击边），使下游
`TerminalPolicy`/`adoptedStep` 有载体可挂。

**证明义务**：
1. 论点集有穷（`Finset Arg`），且对构造所用的 CaseFile 字段是**函数式**的
   （同一份案卷必得同一台框架）；
2. 攻击边良构：`attacks ⊆ args × args`（没有指向框架外的边）；
3. 构造对字段的依赖逐字段说清——哪个 CaseFile 字段生成哪些论点、哪些边，
   不在依赖表里的字段改动不得改变框架（自由数据定理，同 WBS-4 的
   `case_burden_field_is_free_data` 形）；
4. 与 `hornOfCase` 的关系写明：闭包命名像里的原子与论点标签之间的映射须另证
   一一对应，不得沿用 G6 轮"两个标签手工对齐"的夹具做法。

**需要的输入字段**（现 `CaseFile` 没有，须增栏或外挂）：
- 争点表：本案哪些主张成对冲突（每对至少一条攻击边的候选）；
- 攻击关系声明：哪条规范／哪个事实攻击哪个主张——带案卷自报引注；
- 主体栏：每个主张的提出方（举证责任分配的前提）。

**哪一步实质是法律判断而非管道**：攻击边的**存在性**（"这份证据是否攻击那个
主张"、"这个抗辩是否压倒那个请求"）是法律评价，JSON schema 生成不了；管道只能
搬运案卷已声明的攻击边。争点归纳同样是法律判断。

## 二、段二：→ `admissibleSupport`（支持位判定）

**目标**：给出 `Arg → Bool` 的支持位函数，使"举证不能 ⇒ 不被采纳"在案卷载体上
落地（第 90 条第 2 款的机器入口，现为 `chain_art90_gate_has_input_witness` 的
夹具形态）。

**证明义务**：
1. 支持位与闭包的一致性方向必须选定并证出：现行 `instanceM` 取"在 Horn 闭包
   命名像里 ⇒ 支持"，该方向在案卷载体上是否沿用须先证映射保真（段一第 4 条）；
2. 若支持位要进 `adoptedStep` 的过滤条件，须证该载体的 `round > 0` 或另立
   第 0 层之外的入口——现 `instanceM.round = 0` 使支持位根本不进采纳步，
   这一空转已由 `instanceM_pol_not_adopted_consistent` 登记，新通道不得复制；
3. 与 `caseBurden` 栏（WBS-4 三定理）的读数分工：案件栏"已举证／未举证"与
   Horn 侧"在命名像里"谁是支持位的权威来源，只能二选一，另一个降为观测。

**需要的输入字段**：每个事实位与每条规范前提的举证状态（现 `caseBurden`
雏形在 `UnifiedModel` 上，案卷侧无对应栏）、证明责任分配声明（主张→承担方）。

**哪一步实质是法律判断而非管道**：证明责任分配（91 条现仍为恒等式
`art91BurdenOf`，本规格不消化该缺口）、证据充分性评价（"证据不足以证明其
事实主张"的认定）。

## 三、段三：→ `EvalDomain`（评价域与证明标准档）

**目标**：为案卷给出证明标准档的落点，使第 108 条高度可能性／第 109 条五类
更高标准在案卷载体上有入口。

**证明义务**：
1. 评价域命名合法：不得把法定出口款读成可点名域（`escape_tier_cannot_name_a_nonblank_domain`
   族的边界继续有效）；
2. 第 109 条五类事项的归类来源须从夹具 `factMatterClass` 换成案卷声明，
   并证"归类错误时档位不落"（fail-closed）；
3. 与裁决结论的挂接形状：评价域读数如何进 `Judgment`，须遵守对象定义 v3
   的分层（`Judgment=不成立 ⇏ Truth=false`），不得把档位读数直接编码成
   实体结论——那条是双向字典红线的近亲。

**需要的输入字段**：案件类型声明、待证事实类别声明（五类更高标准事项的
归类依据）、程序阶段标记（判决前／后，90 条 2 款的时间窗）。

**哪一步实质是法律判断而非管道**：待证事实归入五类事项、高度可能性的心证
评价——这两步原则上不可机械化，管道只能搬运法官／案卷已作的归类并保证
档位运算忠实。

## 四、边界声明

- 三段全部落地前，禁止任何"案卷进模型跑通裁决链"的对外表述；
  门禁 `scripts/ci/check_statute_chain_caseinput_claim.py` 已在文案层判红该类句子。
- 本规格不消化 91 条恒等、证明妨碍查无、释明义务无后果三个独立缺口，
  它们各有队列位置。
- 段一的"映射保真"与段二的"空转回避"是开工前的两个**先决证明**，
  证不出就停在规格层，不许用新夹具充数。
