## 第一章 · 分层框架

### 1.1 七层两横切（法律语义轴）

| 层 | 名字 | 一句话 |
|---|---|---|
| L0 | 概念层 | 法律概念的户籍簿：什么叫做"请求权""时效""构成要件"，每个概念一条定义、一个编号 |
| L1 | 法源层 | 法条、判例、司法解释的真身：哪个版本、现行吗、位阶多高、何时生效 |
| L2 | 问题与要件层 | 先判断这是什么法律问题（定性/争点），再拆构成要件 |
| L3 | 证明与责任层 | 证据进不进得来、证明到什么程度、举证责任在谁 |
| L4 | 论证与裁量层 | 双方怎么攻防、条文怎么解释、量刑怎么量、谈判怎么谈 |
| (L5) | 计算与保证层 | 机器内核：规则推演、金额计算、证书签发。加括号=机器自动过，非人工站 |
| L6 | 交付与工作台层 | 文书、审计视图、人机复核包——交到用户手里的东西 |

**贯穿桶**：时间概念（期间/时效/期日）服务 L0–L6 全栈，不单设一层，独立成桶排序。

**两横切**（贯穿规矩，不占序位）：
- **横切 A 经验校准**：真实数据（文书库、检索、胜诉率、偏离度、倾向）从这条进系统喂参数；
- **横切 B 回执**：每层每句输出必须带可主张等级——结论级（有证书）/参考级（仅供参考）/不可主张（没依据）；无回执层自动降不可主张（机读账本 `theory/spec/receipt_ledger.json` 已施）。

**办案流程**：①定性 ⇄ ②找法 → ③定要件 → ④证据证明 → ⑤论证裁量 → (⑥机器计算) → ⑦交付。判断在前，找法在后。

**三把尺子，三个名字，永不混用**：
- **层** = 本总谱的法律语义七层（L0–L6）；
- **轨** = jusbench 改动节奏七轨（算法/规则/知识/数据/维护/账本/产品）；
- **序** = 证明目标的依赖位序（本总谱 P 序）。
两套"七"不同轴：本谱七层管法律语义，jusbench 七轨管改动频率，互不换算、引用必须带轴名。

### 1.2 内核对象条款（冻结，原样吸收自对象定义 v3）

设条件组：法域环境 J（含适用范围）、规范环境 V、证据状态 e、时点 t，及事件历史时间结构 H。

1. **对象**：法律关系整体状态 B_t = (R_t, K_{e,t})。R_t 为规范本体状态；K_{e,t} 为现有证据及证明规则下的认知/可支持状态集合。关系整体含共同约束（同一损失、竞合互斥、共同消减）。
2. **真值与判断分层**：Truth(q, R_t) ∈ {true, false} 为规范本体语义；Judgment(q | K_{e,t}, P, V) ∈ {成立, 不成立, 未决} 为给定证据、证明责任与程序状态下依法可支持的判断。**Judgment=不成立 ⇏ Truth=false**，除非规范另有构成效果。
3. **求值**：Eval(q) = (Judgment(q), Disposition(q))，q 分实体/程序/效力型；Disposition ∈ D ∪ {∅} 为程序法律效果字段，不与三值竞争；程序主张的确定 Judgment 不自动生成实体主张的 Judgment。
4. **事件与转移**：有法律效果的事件依规范作用于 R_t，证据更新原则上作用于 K_{e,t}，同一事件作用二者须分别说明依据。裁判事件：R_{t+1} = T(R_t, EffectType(JudgmentEvent))，确认性裁判不得实现为创造关系，仅形成性裁判产生实体状态转移。
5. **类型模态**：Power（可以实施/产生法律效果）、Obligation（依法应当/不实施）、Occurred Event（事实上/法律上已发生）——三者互不推出（无一般性无条件蕴含，具体规范可建立条件性推导）。
6. **规范选择**：ApplicableNorm = A(J, V, q, H, t)，H 承载相关事实/事件时间结构；t 不单独决定版本。
7. **未决条件**：必要材料缺失且穷尽举证责任/推定/证明妨碍/程序终结规则仍不能判定时输出未决；证明失败的法律后果是合法结论。
8. **派生分析**（独立目标类型，非内核对象本身）：概率外衣=胜诉率（显式目标总体/结果变量/观测机制，不可识别即 UNKNOWN）；行为外衣=DecisionProgram；对比外衣=偏离度三算子与倾向分层。
9. **边界**：六类不可表达边界定理未证=UNKNOWN，仅作边界管理不作封闭主张；缺证据永不冒充结论。

**实现警告**（违反=实现不符规格，非改定义）：K_{e,t} 不得偷换单一"当前最可能状态"——它是候选状态集合；Disposition 不得重新编码成 Judgment 的枚举成员；裁判事件不得统一实现成"判什么 R 就变什么"。
现状：条款 1–7 已双侧落地（Python 合同 `theory/spec/canonical_v2/kernel.py` + Lean `JurisLean/KernelV3.lean` 14 定理，CI 全绿）。

## 第二章 · 排序规则

1. **层序**：证明按 L0 → 贯穿 → L1 → L2 → L3 → L4 → (L5) → L6 → 横切A → 横切B 推进。理由：L0 是词汇表（后面每层的陈述都要用这些词说话）；时间结构是词汇表的一部分但服务全栈；L1 供法源（要件涵摄要引用哪一版法）；L2 定性、L3 定证明、L4 定论证（办案序）；(L5) 给全栈算的保证件；L6 交付收尾；横切 A/B 的概念件排尾部，但其**证明允许与所服务层并行**（依赖允许时）。
2. **层内拓扑序**：同桶内谁是谁的前置谁排前（如"法律关系"在"请求权"前）。桶内顺序为**初始证明序**；证明战役中若发现依赖倒置，允许桶内换序，须在执行台账留痕。
3. **全局序号 P-001..P-132**：说到"做到 P-047"即唯一所指，不再有版本歧义。谱号（A/B/C/D 编号）保留为别名列，跨账本引用带前缀（`谱:A30`、`仓:T122`）。
4. **户籍/干活双栏**：概念户籍永远在 L0（概念系统）或 L1（法源供货概念：A1–A7、A61–A63）；干活层=它在哪层被使用，可多地。排序按**主干活层**（桶），次层记录在表注。
5. **桶归属判据**（自审用）：概念的主要服务对象在哪一层，桶就在哪层；词汇性概念（概念系统自指件、主体/关系/权能本体）主服务即概念系统自身→L0 桶；计算族概念的语义主层在前、(L5) 为其保证面记次层。
